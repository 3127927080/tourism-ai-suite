# 旅游智能客服 · 交付说明（窗口二）

> 范围：`customer-service`（8000）+ `ai-service`（8002）+ `tourism-service`（8001）+ 前端（user 5173 / admin 5174）。
> 依赖（窗口一）：知识库 Knowledge Service 8005；未就绪时知识类问答走**平台规则兜底 + 降级**（已在验收中豁免）。

## 1. 架构与端口

| 服务 | 端口 | 说明 |
|---|---|---|
| Customer Service | 8000 | 会话/消息/Turn/工单/Outbox/WebSocket；`Conversation.task_state` |
| Tourism Service | 8001 | 旅游业务数据（产品/订单/出行/退款/工单），只读 + 受控写接口 |
| AI Service | 8002 | Agent：工具/Skill/校验/TaskState/NDJSON 流式/评测 |
| Knowledge Service（窗口一） | 8005 | 旅游知识检索（只返回片段） |
| user-frontend | 5173 | 旅客端（产品/聊天/订单/出行/退款） |
| admin-frontend | 5174 | 人工工作台（工单接入/回复/结束）+ 监控 |

基础设施：PostgreSQL `192.168.200.188:5432`（库 `customer_service` / `ai_customer_service` / `tourism`），Redis `192.168.200.188:6379`（Pub/Sub）。

## 2. 启动顺序

```powershell
# 0) 首次或结构升级：各服务建表（幂等）
cd tourism-service;   uv sync; uv run python -m tourism_service.reset_data   # 可选：重置种子
cd ai-service;        uv sync; uv run python -m atguigu.infrastructure.init_db
cd customer-service;  uv sync; uv run python -m atguigu.infrastructure.init_db

# 1) 业务数据服务
cd tourism-service;   uv run python -m tourism_service.server              # 8001

# 2) AI 服务
cd ai-service;        uv run python -m atguigu.main                        # 8002

# 3) 会话服务（三个进程）
cd customer-service
uv run python -m atguigu.main                      # API 8000
uv run python -m atguigu.worker.ai.worker          # AI Worker
uv run python -m atguigu.worker.realtime           # Outbox Worker

# 4) 前端
cd 前端服务\user-frontend;  npm install; npm run dev                        # 5173
cd 前端服务\admin-frontend; npm install; npm run dev -- --port 5174          # 5174
```

- 前端 `.env` 指向本地：`VITE_CUSTOMER_SERVICE_URL=http://127.0.0.1:8000`、`VITE_TOURISM_SERVICE_URL=http://127.0.0.1:8001`、`VITE_AI_SERVICE_URL=http://127.0.0.1:8002`。
- `.env` 不入库，参照各目录 `.env.example`。
- 模型：`LLM_THINKING_MODE=enabled`（仅 `deepseek-v4.1-flash` 可用）。

## 3. 接口清单（要点）

**Customer Service**
- `POST /api/v1/chat/messages`：发送消息（`type=text|object`，对象消息 `content={type,id,fields}`）
- `GET /api/v1/chat/history?after_sequence=&limit=`：旅客历史消息（游标增量）
- `POST /api/v1/conversations/current`：当前会话 + `current_task`（任务/槽位）
- `GET /api/v1/conversations/{id}`：会话详情（agent/admin）
- `GET /api/v1/handoffs`、`POST /handoffs/{id}/accept|messages|resolve`：人工工单
- `WS /api/v1/realtime`：事件 `message_delta` / `message_created` / `handoff_changed`

**AI Service（内部）**
- `POST /internal/v1/agent/runs`：NDJSON 流式（`run_delta` + 最终事件）
- `POST /internal/v1/agent/runs/{id}/confirm|cancel`

**Tourism Service**
- 读：`/products?query=&type=`、`/products/{id}`、`/products/{id}/availability`、`/orders`、`/orders/{id}`、`/orders/{id}/trip`、`/refunds`、`/tickets`
- 写（前端确认后调用，带 `Idempotency-Key`）：`POST /orders/{id}/refunds`、`/tickets`、`/cancel`、`PATCH /orders/{id}/travelers`

## 7. 已知限制

1. **模型**：网关仅 `deepseek-v4.1-flash`，短指令/部分表达会偶发 `MODEL_OUTPUT_INVALID`；已有多层重试（AI 纠错 3 + CS 轮次重试 3 + 客户端重发），仍可能失败；验收记录成功率并标注。
2. **8005 未就绪**：知识文档类问答豁免；仅平台规则可答。
3. **CS-13 取消端到端**：Reducer 正确，模型侧不稳定。
4. 语义评测（RAGAS/DeepEval）未接入，仅规则层报告。

## 8. 规则层评测结果（2026-10-23）

命令：
```bash
EVAL_USER_ID=user_001 uv run python -m eval.run_eval --skip-ragas --skip-deepeval
```
报告：`ai-service/eval/results/20261023-024508/`（summary.json / result.csv；该目录被根 .gitignore 忽略，不随仓库提交）。

结果：**20 例，规则通过 8（40%）**。分场景通过率：
- policy 3/4、security 1/1、product 1/1、order 2/3、red_line 1/2
- knowledge_missing 0/3、out_of_scope 0/1、handoff 0/2、trip 0/1、refund 0/2

主要失败类型（模型侧为主）：
1. 兜底类型漂移：越界/知识缺失应 `DECLINE` 却作答（`a_scope`/`a_missing`/`kb_missing`），存在编造风险（示例“支持货到付款”）。
2. 红线表述：出现“为您提交/为您修改”等越权完成时表述（`a_handoff_001`/`c_action_002`）；绝对化承诺“保证”（`a_promise_001`）。
3. 工具选择：出行问法未调用 `get_trip_info`（`c_trip_001`）。
4. 部分 Run 直接失败（空回复：`c_refund_001`/`c_clarify_001`/`a_handoff_002`），即 `MODEL_OUTPUT_INVALID` 兜底失败。

> 说明：仅 `deepseek-v4.1-flash` 可用，结构化输出/兜底判定不稳；以上为现状如实记录，规则层 40% 不达标，后续需更强模型或 Prompt/校验强化。

### 8.1 改进与最新结果（同日）

已实施并验证的改进：
1. 知识降级不再回“暂时无法查询”误导（平台规则仍可用，由相关性规则决定作答）；
2. Prompt 增加：非旅游/无相关依据必须 DECLINE、禁绝对化承诺、禁声称已修改/提交、入住/行程类必须用 get_trip_info；
3. 红线正则去掉“提交转人工申请”误伤，保留真实写操作完成时表述；
4. 评测 Harness 增加 Run 级重试（≤3，对齐 CS Worker 语义）。

结果演进：**40% → 40%（修复生效但被新失败抵消）→ 45%（9/20）**。
最新分场景：policy **4/4**、security 1/1、product 1/1、order 2/3、handoff 1/2；
仍失败：knowledge_missing 0/3、out_of_scope 0/1、red_line 0/2、trip 0/1、refund 0/2。

剩余失败归因：
- **兜底纪律（模型）**：应 DECLINE 却作答/编造（kb_missing×2、a_scope、a_missing）。
- **空回复（模型结构化失败）**：handoff_002、refund、clarify、action，重试 3 次仍失败。
- **工具选择**：trip 未调 get_trip_info。
- **红线/期望口径**：c_action_002 出现“为您变更”（真实越权）；a_promise/a_write 类型不匹配（CLARIFY/DECLINE 与期望 ANSWER/CLARIFY）。

进一步提升建议（按投入产出排序）：
1. **换更强模型**或改用 **provider 原生 json_schema 结构化输出**（直击空回复与兜底漂移，收益最大）。
2. 对“兜底/红线”增加 **few-shot 示例**与更强的拒答约束。
3. 校验层增加“无工具依据的 ANSWER”降级（需区分政策类，避免误伤）。
4. 复核个别数据集期望口径（a_write/a_promise 的类型是否过严）。

### 8.2 结构化输出改造试验（同日）

- **Provider 原生 json_schema（AGENT_RESPONSE_STRATEGY=provider）**：该网关不支持，实测直接“模型调用失败”；已加开关（默认 tool），供换网关时启用。
- **结构化容错降级（已启用）**：`AgentOutput` before-validator 丢弃不合规的可选子结构（page_action/handoff/task_update），避免整轮 `MODEL_OUTPUT_INVALID`。
- 效果：`order` 场景 **3/3**（`c_action_002` 通过）；但总体仍 **9/20（45%）**。剩余失败主要是**模型未产出结构化调用（空回复）**与意图/兜底纪律，非 schema 违规，容错无法覆盖。
- 结论：现有单模型（flash）下，45% 已接近“确定性修复 + 重试 + 容错”的上限；进一步需换更强模型或网关支持原生结构化输出。
