# 旅游智能客服系统项目实战需求说明
## 1. 项目背景与目标
### 1.1 项目背景
在线旅游平台面向旅客、供应商和运营团队提供酒店预订、景区门票、机票/火车票/汽车票、接送服务等一站式出行支撑能力，覆盖产品搜索、预订下单、支付交易、出行服务、售后处理等完整业务链路。随着业务规模扩大，旅客在产品咨询、订单查询、出行信息确认、售后处理等方面的服务请求量持续增长，需要一套智能客服系统来承载这些高频服务场景。

### 1.2 项目目标
构建一个面向在线旅游行业的智能客服系统，支持以下核心目标：
- 自动识别旅客的咨询意图，提供酒店咨询、景区咨询、交通票务咨询、订单查询、出行信息查询等问答能力
- 支持退款申请、工单提交等需要多轮引导的任务型对话
- 在多轮对话中持续收集和利用上下文信息（旅客身份、订单号、出行日期等）
- 所有对话状态可持久化，支持会话恢复和历史回溯

## 2. 用户角色
### 2.1 旅客
核心服务对象。通过智能客服咨询酒店/景区/交通产品信息、查询订单状态、了解出行安排、发起退款或投诉等。

### 2.2 客服人员
承接系统无法自动处理的问题，负责人工兜底、复杂售后处理和工单跟进。

### 2.3 运营人员
维护知识库内容、FAQ 条目和服务流程配置，保障客服系统稳定运行。

## 3. 功能需求
### 3.1 信息检索
系统应能从业务数据和知识库中检索相关信息并以自然语言组织回复，支撑产品咨询、订单查询、出行信息查询、政策咨询等场景。
- 实时业务数据检索：查询酒店、景区、机票、火车票、汽车票、接送服务、订单、支付、退款等动态数据
- FAQ 检索：匹配退改政策、预订规则、出行须知等相对固定的制度性问题
- 知识库检索：检索平台规则、使用指南等通用内容

### 3.2 任务型对话
系统应能通过多轮对话引导用户完成需要收集多项信息才能处理的业务任务。
- 支持订单状态查询：收集订单号 → 查询并返回订单状态、支付情况、预订产品信息
- 支持出行信息查询：收集订单号 → 查询并返回出行日期、行程安排、入住/出游/出发信息、旅客信息等
- 支持退款申请：收集订单号、退款原因、退款类型 → 创建退款申请并返回处理结果
- 支持工单提交：收集工单类型（售后/投诉/退款）、关联订单号、问题描述 → 创建工单并返回工单编号与处理预期

### 3.3 对话管控
系统应具备完整的多轮对话管理能力。
- 支持槽位收集：在任务流程中主动向用户追问缺失的信息（如订单号、出行日期、退款原因）
- 支持上下文保持：在多轮对话中持续利用已收集的旅客信息、订单信息、产品信息
- 支持流程切换：当前任务执行中，用户发起新任务时，暂存当前任务并切换到新任务
- 支持流程恢复：新任务完成后，恢复之前暂存的任务继续处理
- 支持流程取消：用户主动取消当前任务时，清理对应状态并确认取消

### 3.4 闲聊兜底
当用户输入不属于明确的业务任务或信息查询时，系统应能给出自然、友好的闲聊回复，并在适当时候引导用户回到业务场景。

## 4. 典型业务场景
### 4.1 产品咨询
旅客询问酒店、景区、机票、火车票、汽车票、接送服务等产品信息时，系统应结合产品数据返回清晰回复。产品类型包括：
- 酒店：房型、设施、价格、入住/退房时间、位置等
- 景区：票种、价格、开放时间、景点介绍、评级等
- 机票/火车票/汽车票：班次、出发/到达时间、舱位/座位等级、价格等
- 接送服务：服务类型、车型、载客数、区域定价等

```
旅客：三亚有哪些五星级度假酒店？
系统：返回符合条件的酒店列表、房型及价格区间，并引导旅客选择具体酒店了解更多
旅客：G527 这趟高铁什么时候出发？
系统：返回 G527 的出发时间、到达时间、座位等级及价格
```

### 4.2 订单查询
旅客提供订单号后，系统应返回订单状态、支付情况、预订产品等信息。
```
旅客：帮我查下订单 ORD20240501010
系统：返回订单状态（待支付/已支付/已取消等）、预订产品名称、金额、支付时间
```

### 4.3 出行信息查询
旅客询问某订单的出行安排时，系统应返回行程日期、产品详情、旅客信息等内容。
```
旅客：我的订单 ORD20240501010 具体哪天入住？
系统：返回酒店名称、入住日期、退房日期、房型、入住人信息
旅客：下周一我有啥出行安排？
系统：返回该日期的订单列表及对应的行程概要
```

### 4.4 退款申请
旅客发起退款时，系统应收集订单号和退款原因，创建退款申请并反馈处理结果。
```
旅客：我要退款
系统：收集订单号 → 收集退款原因 → 确认退款类型 → 提交退款申请 → 返回确认信息
```

### 4.5 工单提交
旅客遇到服务问题、投诉或需要人工介入时，系统应收集必要信息并创建工单。
```
旅客：酒店房间和预订时描述的不一样，我要投诉
系统：确认工单类型 → 收集关联订单号 → 收集问题描述 → 创建工单 → 返回工单编号
```

## 5. 对话交互要求
### 5.1 消息处理
- 支持接收文本消息和业务对象消息（如旅客发送一个订单或产品对象）
- 收到业务对象消息时，应自动提取对象信息并尝试匹配当前任务所需的槽位

### 5.2 响应模式
- 支持非流式响应（一次性返回完整回复）
- 支持流式响应（通过 SSE 逐字返回回复内容）

### 5.3 会话管理
- 支持创建新会话
- 支持获取会话历史消息
- 支持获取当前会话状态（当前激活的任务流程、已收集的槽位信息）
- 会话状态应持久化存储，支持会话恢复

### 5.4 意图澄清
当系统无法准确判断用户意图时，应主动向用户澄清，而不是直接给出错误回复。澄清场景包括：
- 用户输入同时匹配多个意图
- 用户输入过于模糊，无法确定具体需求
- 当前任务需要的关键信息缺失
- 用户输入与当前任务上下文存在冲突

## 6. 非功能需求
### 6.1 可靠性
- 单次对话处理失败不应影响整体服务可用性
- 对外部业务 API 的调用应具备超时和异常处理能力
- 对话状态保存失败时应有降级处理

### 6.2 可观测性
- 应能追踪每次对话的处理轨迹（意图识别结果、进入的轨道、执行的动作、生成的回复）
- 应能记录关键节点的执行状态和耗时
- 工单处理过程应支持日志记录与审计

### 6.3 准确性
- 查询结果应基于实时业务数据，避免返回过时或错误信息
- 任务流程中的槽位收集应准确提取用户输入中的关键信息
- FAQ 和知识库检索应优先返回最匹配的内容

### 6.4 可扩展性
- 新增任务流程应可通过配置方式实现，无需修改核心代码
- 新增知识意图类型应可灵活扩展
- 新增业务 API 调用应可方便集成

## 7. 项目交付物
- 对话接口与会话管理能力
- 一套可运行的业务样本数据与配置
- 前端调试/演示页面
- 项目说明文档与启动说明

## 8. 验收标准
1. 能够完成酒店咨询、景区咨询、交通票务咨询、订单查询、出行信息查询等基础问答
2. 能够在多轮对话中持续收集和使用旅客身份、订单号、出行日期等槽位数据
3. 能够完成退款申请、工单提交的完整多轮任务流程
4. 能够完成一次完整的"用户提问 → 意图识别 → 业务查询/流程处理 → 生成回复 → 状态更新"闭环演示
5. 对话状态可持久化，支持会话恢复
