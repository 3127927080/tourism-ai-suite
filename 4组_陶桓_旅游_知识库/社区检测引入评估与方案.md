# 社区检测（Community Detection / Leiden）引入评估与实施方案

> 评估对象：`d:/pycharm-0515-th/kb_0515` GraphRAG 项目
> 评估方式：只读走查现有图谱数据模型、图检索节点、查询链路配额逻辑、依赖清单
> 结论先行：**现阶段不建议做，先做 3 项前置改造；改造完成后按「触发条件」再上。**

---

## 一、先在概念上对齐：社区检测解决什么、不解决什么

微软 GraphRAG 的社区检测 = **Leiden 层级聚类 + LLM 生成社区摘要（Community Report）**，它解决的是 **Global Search（全局归纳类）** 问题：

- 「整个知识库里存在哪些主题/风险类别？」
- 「跨文档来看，A 类产品和 B 类产品在安全设计上有什么共性？」
- 「给我一份这个知识库的综述」

它**不解决** Local Search（事实/关系型提问）——那类问题是「实体邻域检索」的活，本项目现在的 `node_search_graph.py` 已经覆盖了一部分。

**关键判断依据**：引入社区检测的收益，完全取决于**「全局归纳类问题」在真实流量中的占比**。而这个占比在本项目里目前接近 0（见 §二.5）。

## 二、现状体检：6 项前置条件逐条核对（带证据）

| # | 前置条件 | 现状 | 证据 |
| --- | --- | --- | --- |
| 1 | 图是否有**来源溯源**（关系能追到文档/商品）？ | ❌ **完全没有**。边的属性只有 `type`，节点属性只有 `name` | `node_graph_import.py:65-71` 的 Cypher 只写 `Entity{name}` 与 `RELATES{type}`，无 `file_title`/`item_name`/`weight`/来源切片 ID |
| 2 | 是否做过**实体消歧/归一化**？ | ❌ 没有，且项目自认这是技术债 | `GraphRAG项目总结与面试指南.md:431`（§11.1）明确写出「未做实体消歧/归一化」；实测数据里 `HAK 180烫金机` / `HAK180` / `HAK 180 烫金机` 是三个独立节点（`node_graph_import.py:99-105` 的测试数据可见） |
| 3 | 图的**规模与密度**是否支撑有意义的社区结构？ | ⚠️ 规模偏小、密度偏高。单份手册就抽出数百条三元组，实体多为短句片段 | `node_graph_import.py:99-105` 内联的测试数据量级；`node_graph_extract.py:39` `BATCH_SIZE=4`，每 chunk 平均产出十几条三元组，噪声大 |
| 4 | 是否存在**有价值的跨文档关联**？ | ❌ 名义上跨文档（按 `name` MERGE），实际是**错误合并**：泛化实体 `设备`/`用户`/`电源线`/`本设备` 会把所有文档连成一张网 | `node_graph_import.py:68` `MERGE (h:Entity {name: t.head})` 无任何领域/文档隔离；抽取时也未带 `item_name`（`node_graph_extract.py:47-48` 只取 `chunk["content"]`） |
| 5 | 是否存在**全局归纳类**查询需求？ | ❌ 当前两个对外服务都没有这类场景 | `query_service.py` 是单商品问答（问题必带商品名，见 `node_item_name_confirm.py:134-142` 的商品名对不齐就直接澄清）；`knowledge_service.py:1` 明确「只返回检索片段，不生成对话答案」 |
| 6 | 现有图检索是否已把「局部关系检索」榨干？ | ❌ 没有，还有大量未做的低成本优化 | `node_search_graph.py:236` 只做 **1-hop** `MATCH (e)-[r:RELATES]-(related)`，且**没有 item_name / file_title 过滤**（全文无该字段），意味着查 HAK180 可能召回其他商品的边 |

### 由第 4 条引出的致命技术结论

因为第 1、2 条缺失 + 第 4 条的「按字面名 MERGE」，当前图谱大概率是**一个巨型连通分量（giant component）**：
`设备`、`用户`、`水`、`电源线` 这类高频泛化实体在每个商品文档里都会出现，它们把这些文档**强行缝合**成一张网。

**在这样的图上跑 Leiden，产出的社区是"由泛化词缝合而成的任意分组"，不是"语义主题"。** 微软 GraphRAG 之所以要先做实体消歧 + 高质量抽取，正是因为社区质量对这些前置步骤极度敏感。所以：**现在做社区检测 = 在一个被污染的图上做聚类，投入产出比接近 0，而且结果不可用。**

## 三、量化评估

### 收益侧

| 收益 | 现阶段可得性 |
| --- | --- |
| 支持「全局归纳类」问答 | 无需求，收益≈0 |
| 提升跨文档多跳关系问答 | 有需求，但**多跳路径检索**能以 1/5 的成本解决，不需要社区 |
| 辅助图谱可视化 / 主题浏览 | 有微弱价值（前端仅 `web/page/chat.html`、`import.html`，且未挂载静态资源） |
| 缓解「关键词匹配脆弱」（`§11.3` 已自认的技术债） | **有真实价值**，但应先修关键词抽取与实体归一，社区检测不是对症药 |

### 成本侧

| 项目 | 成本 |
| --- | --- |
| 新增依赖 | `python-igraph` + `leidenalg`（Windows/Py3.12 有 wheel，约 10MB）；**注意 `networkx`、`scipy`、`scikit-learn` 已在 `uv.lock` 中间接存在**，可零新增依赖先用 Louvain 做基线验证 |
| 离线任务开发 | 构图 + 聚类 + 落库 ≈ 1~2 天 |
| 社区报告生成 | **主要成本**。每个社区 1 次 LLM 调用，多分辨率层级会让调用量翻倍；语料增长时线性上升 |
| 查询链路改造 | 新增第 5 路召回 + 重写配额逻辑 + 新增 `global` 意图类型，约 3 天 |
| 一致性维护 | 新文档入库后社区结构失效，需要重建策略（Leiden 无稳定增量算法，只能全量重跑） |
| 风险 | 社区报告 LLM 幻觉；报告与图谱不同步（stale）；Rerank 候选变多导致延迟上升（Rerank 是远程 DashScope 调用，已是链路瓶颈） |

**结论：收益≈0 而成本≈1 周 + 持续 LLM 开销 → 现阶段 ROI 为负。**

## 四、建议：分阶段推进，社区检测放在最后一档

### Phase 1（立刻做，1~2 天）—— 社区检测的必要前提，且**独立就有收益**

**1.1 给图谱加 provenance 与权重**

```cypher
// node_graph_import.py 的写入语句改造成：
UNWIND $triples AS t
MERGE (h:Entity {name: t.head})
  ON CREATE SET h.first_seen = timestamp()
SET h.doc_count = coalesce(h.doc_count, 0)   // 需按批去重后统计
MERGE (tail:Entity {name: t.tail})
MERGE (h)-[r:RELATES {type: t.relation}]->(tail)
  ON CREATE SET r.weight = 1
  ON DUPLICATE SET r.weight = r.weight + 1,
                  r.sources = coalesce(r.sources, []) + [t.file_title]
```
同时 `node_graph_extract.py` 抽取时要**带上 `item_name`/`file_title`**（现在 `node_graph_extract.py:47-48` 完全没用），三元组结构从 `[head, rel, tail]` 扩展为带来源的 dict。

**1.2 给图检索加领域过滤（顺手修掉跨域污染）**

```python
# node_search_graph.py:235-246 的关系查询加一层约束
relation_query = """
MATCH (e:Entity {name: $entity})-[r:RELATES]-(related:Entity)
WHERE r.type IN $relation_types
  AND (r.sources IS NULL OR ANY(s IN r.sources WHERE s IN $file_titles))
RETURN ...
"""
```
或者更简单：`Entity` 增加 `item_names` 属性，实体匹配时就按 `item_names` 收窄（对齐已有的 `item_names` 状态字段）。

> ⚠️ 这一步**必须**先做。否则后续任何图算法（包括社区检测、多跳检索）都是在错误合并的图上运算。

### Phase 2（建议做，2~3 天）—— 比社区检测性价比更高的替代方案

**2.1 实体归一化**
- 规则层：大小写/空格/全半角归一 + 别名表（`HAK 180` → `HAK180`）
- LLM 层：批量让模型判断「这些实体名是否指同一事物」，产出 alias 映射
- 存储层：`CREATE CONSTRAINT entity_name_unique FOR (e:Entity) REQUIRE e.name IS UNIQUE`，并增加 `e.aliases` 数组；检索时 `WHERE e.name IN $aliases`
- 泛化实体治理：建一张**停用实体表**（`设备`、`用户`、`本设备`、`本文档`、`手指`…），抽取阶段就过滤掉，或至少给它们打 `is_generic=true` 标记，聚类/检索时降权

**2.2 多跳路径检索**（社区检测最直接的替代品）
```cypher
MATCH path = (e:Entity {name: $entity})-[r1:RELATES*1..2]-(related:Entity)
WHERE ALL(rel IN relationships(path) WHERE rel.type IN $relation_types)
RETURN path LIMIT $limit
```
这能直接回答「A 和 B 有什么关系」这类关系型问题，成本远低于社区检测。

### Phase 3（触发式，5 天左右）—— 上图，推荐方案 A

**方案对比**

| | 方案 A：Python 离线聚类（推荐） | 方案 B：Neo4j GDS 插件 |
| --- | --- | --- |
| 实现 | `igraph` + `leidenalg`，Neo4j 只做数据源与结果落库 | `gds.leiden.write` / `gds.louvain.write` |
| 优点 | 无插件运维；参数（resolution/seed）完全可控；易调试、易离线复跑；可在 Python 侧做多分辨率层级与规模过滤 | 图不落地，内存与事务由 DB 管；支持在线增量算法 |
| 缺点 | 需把图拉到 Python（几千节点量级无压力） | 社区版 Neo4j 不含 GDS，需换镜像/装插件；GDS 版本须与 Neo4j 主版本严格对齐 |
| 结论 | ✅ 本项目规模小、Python 生态成熟，选 A | 语料涨到十万级节点再考虑 |

**落地骨架**

```python
# atguigu/tool/community_tool.py（新文件）
import igraph as ig
import leidenalg
from atguigu.tool.neo4j_client_tool import get_neo4j_driver
from atguigu.tool.logger import logger

GENERIC_ENTITIES = {"设备", "用户", "本设备", "本文档", "手指", "水"}  # Phase 2 产出的停用表

def fetch_weighted_edges():
    cypher = """
    MATCH (h:Entity)-[r:RELATES]->(t:Entity)
    WHERE NOT h.name IN $generic AND NOT t.name IN $generic
    RETURN h.name AS head, t.name AS tail, coalesce(r.weight, 1) AS w
    """
    with get_neo4j_driver().session() as s:
        return list(s.run(cypher, generic=list(GENERIC_ENTITIES)))

def detect(resolution: float = 1.0, level: int = 0):
    rows = fetch_weighted_edges()
    nodes, index, edges, weights = [], {}, [], []
    for rec in rows:
        for name in (rec["head"], rec["tail"]):
            if name not in index:
                index[name] = len(nodes); nodes.append(name)
        edges.append((index[rec["head"]], index[rec["tail"]]))
        weights.append(rec["w"])
    g = ig.Graph(n=len(nodes), edges=edges, directed=False)
    g.es["weight"] = weights
    part = leidenalg.find_partition(
        g, leidenalg.RBConfigurationVertexPartition,
        weights="weight", resolution_parameter=resolution, n_iterations=-1, seed=42,
    )
    logger.info(f"level={level} resolution={resolution} 社区数={len(part)} modularity={part.modularity:.4f}")
    return [
        {"cid": f"L{level}-{cid}", "level": level, "size": len(members),
         "members": [nodes[i] for i in members]}
        for cid, members in enumerate(part)
    ]

def write_back(communities):
    cypher = """
    UNWIND $rows AS row
    MERGE (c:Community {community_id: row.cid})
    SET c.level = row.level, c.size = row.size
    WITH c, row
    UNWIND row.members AS member_name
    MATCH (e:Entity {name: member_name})
    MERGE (e)-[:IN_COMMUNITY]->(c)
    """
    with get_neo4j_driver().session() as s:
        s.run(cypher, rows=communities)
```

**社区报告生成（成本控制要点）**
1. **只对 top-level + `size >= 5` 的社区生成报告**，小社区跳过（否则 LLM 调用量爆炸）
2. 分层汇总：level 1 报告读 level 0 报告，不重复送原始三元组
3. 报告落库三选一：Neo4j 存文本 + Milvus 存向量（新建 `kb_community_reports` collection，需在 `MilvusConfig` 加配置项）+ Mongo 存原始 JSON。**推荐 Neo4j 存文本、Milvus 存向量**，直接复用现有 `create_reqs`/`search_hybird` 工具
4. 模板里强制要求「只依据给定关系，不得引入外部知识」，降低幻觉
5. 幂等：重建时按 `Community {community_id}` 先删后写（与项目既有幂等风格一致）

## 五、触发条件：什么时候该做

满足**全部 3 条**再进入 Phase 3：

1. **需求侧**：出现明确的全局归纳类需求，且占实际查询量 > 20%（例如客服侧开始问「哪些型号存在触电风险」）
2. **规模侧**：语料跨越 ≥ 3 个领域 / ≥ 20 份文档，实体数（归一化后）≥ 500
3. **结构侧**：归一化 + 泛化实体治理后，**最大连通分量 < 全图的 50%**（否则说明图仍被泛化词缝合，聚类无意义——这是最硬的技术门槛）
